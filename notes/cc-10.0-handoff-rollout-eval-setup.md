# cc-10.0 — Handoff: getting **rollout-based evaluation** running (retail & finance)

How to stand up the *interactive* evaluation — where the policy acts in a live RL
environment and is scored on task completion — as opposed to the teacher-forced
`eval_actiononly_ppl/accuracy` numbers that Stage-2 logs. Covers uv/venvs, the GitHub
dependency, the data downloads, auth, and the failure modes that make a rollout run
produce a plausible-looking but meaningless zero.

Design rationale for the two domains lives in `cc-retail-2.0-rl_eval_tau2_map.md` and
`cc-finance-2.0-rl-design.md`; this is the operational runbook.

---

## 0. First, the naming trap: **there is no "tau2 finance"**

These are two *different environment stacks* that happen to share a driver pattern:

| | retail / airline | finance |
|---|---|---|
| env `name:` | `tau2bench` | `snorkel_finance` |
| env config | `configs/environments/tau2bench/retail_rlvr.yaml` | `configs/environments/act_prm/snorkel_finance_gym.yaml` |
| implementation | wraps τ²-bench's `AgentGymEnv` | custom `SnorkelFinanceEnv` in this repo |
| needs GitHub clone | **yes** (`tau2-bench`) | no |
| data | `tau2-bench/data` (from the clone) | `data/snorkel_finance/{raw,benchmark}` |
| scoring | tau2's own end-of-episode evaluator + NL-assertion judge | LLM judge over the `finqa_reasoning` answer |
| driver | `scripts/run_sft_rollout_eval.sh` | `scripts/run_finance_rollout.sh` |

Picking `--env_config tau2bench/...` for finance (or vice versa) is the single easiest way
to waste an afternoon. Insurance has its own gym too
(`act_prm/snorkel_insurance_gym.yaml`), same pattern as finance.

**Both run in `.venv-tau2`.** The comment at the top of `snorkel_finance_gym.yaml` saying
finance "runs in the base .venv" is **stale** — `run_finance_rollout.sh:53` sets
`UV_PROJECT_ENVIRONMENT=.venv-tau2`, and so does `train_rl_from_sft.sh:51`, which the tau2
path goes through. Trust the scripts, not that comment.

## 1. uv and the two virtualenvs

The repo is a uv project (`act-prm` distribution, `act_prm` import package under `src/`).
There are **two** environments and they must not be conflated:

```bash
uv sync                                                   # -> .venv        (training stack only)
export https_proxy=http://fwdproxy:8080 http_proxy=http://fwdproxy:8080
UV_PROJECT_ENVIRONMENT=.venv-tau2 uv sync --extra tau2    # -> .venv-tau2   (+ tau2, litellm, claude-agent-sdk)
```

`.venv-tau2` is a superset; it exists so an in-flight Act-PRM/SFT run in `.venv` is never
disturbed by installing the rollout dependencies. Base deps hardlink out of uv's cache, so
the second sync is cheap — only `tau2`, `litellm` and `claude-agent-sdk` are genuinely new.

Anything invoking the gym must therefore be prefixed:

```bash
UV_PROJECT_ENVIRONMENT=.venv-tau2 uv run --no-sync python main_pytorch.py ...
```

`uv run --no-project` (used by the small analysis scripts) is a *different* thing — it
ignores the project entirely and is fine for CPU-only helpers.

## 2. The GitHub dependency (the one manual step)

`pyproject.toml` declares `tau2 = { path = "tau2-bench" }` — a **local path**, not a git
URL, because **github.com is blocked by fwdproxy (403)** from this box. So `uv sync` cannot
fetch it and the clone has to come from a shell that reaches GitHub (your own terminal
does; the agent's does not):

```bash
git clone --branch v1.0.0 https://github.com/sierra-research/tau2-bench.git
```

It must land at `./tau2-bench` (gitignored). `retail_rlvr.yaml` reads `data_path:
tau2-bench/data`, so the clone supplies both the package *and* the task/tool data —
there's no separate tau2 data download. Verify with:

```bash
ls tau2-bench/data          # -> tau2  voice
```

If `uv sync --extra tau2` fails with a path-not-found on `tau2-bench`, this clone is the
missing step. Finance needs none of this.

## 3. Data

**tau2 (retail/airline)** — comes with the clone. Nothing to download.

**finance** — the gym reads two local paths that are committed/derived in-repo:
```
data/snorkel_finance/raw/                     # the 10-K tables the SQL tools query
data/snorkel_finance/benchmark/finqa_reasoning.csv   # the questions + gold answers
```

**Models** — Qwen3-4B-Instruct-2507 etc. load from the local HF cache. The rollout scripts
set `HF_HUB_OFFLINE=1` / `TRANSFORMERS_OFFLINE=1`, so nothing is fetched at run time. On a
fresh box, prefetch first (`scripts/prefetch_models.sh`, which sets the proxy + `HF_TOKEN`);
the cache is per-box at `/data/users/$USER/models/hf_cache` and is **not** dotsynced.

> Pin `HF_HOME=/data/users/$USER/models/hf_cache` explicitly in any driver you write. An
> interactive shell can carry `HF_HOME=/home/$USER/models`, which points away from the
> populated cache and silently triggers a re-download. Bit the Stage-2 driver on 08-29.

**Which tasks to evaluate on** — never-trained-on sets, resolved via committed maps:
```
retail  : 42 never-in-logs tau2 tasks   data/splits/tau2_retail_uid_to_tau2id.json   (78 entries)
airline : 18 unseen tau2 ids            data/splits/tau2_airline_taskmap.json
finance : 10 "fair" v3 eval questions + 29 "hard" expert-failure questions
```
The finance *fair* and *hard* sets are **reported separately and never pooled** — the hard
set is selected for difficulty (no successful expert trajectory exists), so a combined
number is meaningless.

## 4. Auth for the user simulator + judge

Both stacks drive an LLM through a litellm custom provider for the **user simulator** and
the **NL-assertion judge**. Two backends are wired:

- `claude_agent_sdk/<model>` → `litellm_claude_agent_sdk.py` → `ClaudeQueryLLM` — **default**.
  On a devserver with Claude Code logged in it uses that ambient session, no key needed.
  Headless: put `CLAUDE_CODE_OAUTH_TOKEN=sk-ant-oat01-...` in `.env` (gitignored).
- `metagen/<model>` → `litellm_metagen.py` → Llama-API passthrough; needs
  `LLAMA_API_KEY=LLM|<id>|<secret>` in `.env`.

`retail_rlvr.yaml` uses `claude_agent_sdk/claude-haiku-4-5` for all three roles
(`user_llm`, `nl_assertions_llm`, `env_interface_llm`).

> `run_finance_rollout.sh` clears `CLAUDECODE=` before invoking python. Keep that when
> writing new drivers: with `CLAUDECODE` inherited, the Agent SDK can behave as though it's
> nested inside a Claude Code session.

## 5. Running it

**Eval-only mode** is `--no_train --num_batches 1 --eval_every 1` — batch 0 is also the
last, so the trainer evaluates, generates one throwaway train batch, and skips the
optimizer step. That's why you'll see a `--train_task_ids` with a single dummy id.

```bash
# retail / airline — all finished hide-regime Stage-2 checkpoints
setsid nohup ./scripts/run_sft_rollout_eval.sh > /tmp/aprm/rollout/driver.log 2>&1 &
SMOKE=1 ./scripts/run_sft_rollout_eval.sh      # 1 ckpt, 1 task, 4 turns — validates the user-sim path FIRST

# finance
./scripts/run_finance_rollout.sh
```

Always run `SMOKE=1` before a full sweep. It exercises the whole Claude-Agent-SDK path in
about a minute; without it an auth or outage problem shows up only after hours of episodes
that all die on turn 1.

`--hide_observations` should match how the checkpoints were trained (the Stage-2 hide
regime), otherwise the policy sees a context it was never trained for.

## 6. `max_turns` — the setting that silently zeroes a domain

**Set it from the expert trajectories, not from the config default.** Finance's env default
of 12 covers only 61% of the 116 v3 expert demonstrations (assistant turns: p50 = 11,
p90 = 19, max = 24). At 12, *every* arm scored 0/10 with `timesteps=0` and a final message
of "Sorry, you have reached the maximum number of steps" — the policy never reached
`respond_user`, so no answer was ever graded. The cap, not the policy, was the binding
constraint. `run_finance_rollout.sh` therefore uses `MAX_TURNS=24`. `retail_rlvr.yaml`
ships `max_turns: 30`.

Measure this per domain before trusting any rollout number.

## 7. Validity gating — do not bank a zero you haven't checked

A transient Claude Agent SDK outage makes every episode die on turn 1, which the trainer
records as a perfectly well-formed `0/N correct`. That is **indistinguishable from a real
result** unless you look at `timesteps` / generate-call counts. It happened on 08-22
(01:35–02:09): 8 full-context rollouts returned 0/42 and 0/18 with `timesteps=1.0` and
exactly one generate call per task.

`scripts/check_rollout_valid.py <run_dir>` is the gate. It fails a run when the
generate-calls-per-task ratio implies episodes died immediately, or when LLM query errors
dominate:

```
check: INVALID -- 0/126, only 42 generate calls (0.33/task); episodes died on turn 1
```

The drivers refuse to write a `.done` marker for an INVALID run so it is retried rather
than recorded as a finding. **Keep that behaviour in anything new.** Related: a driver
should not touch `ALLDONE` unconditionally — doing so is how a wholesale failure (10/10
finance rollouts dying on HF DNS, 08-23) got recorded as a completed stage and the guard
advanced straight past it.

> Corollary learned 08-29: an arm that is *permanently* invalid will be retried forever by
> `sweep_guard.sh` (`*/5` cron). `expert_thoughts` x3 looped for hours on
> `0/126 ... died on turn 1`. If you stop such a loop by touching `ALLDONE`, leave a
> `STOPPED.txt` next to it saying the marker is a stop, not a success.

## 8. Ops gotchas

- **Proxy under cron.** Cron jobs do not inherit your shell's proxy. A rollout driver that
  needs HF will die on DNS in ~18s (08-23, all 10 finance rollouts). Export
  `https_proxy`/`http_proxy` inside the script, not in the calling shell.
- **W&B is unreachable through fwdproxy** (`api.wandb.ai` → curl 000). Source
  `scripts/wandb_preflight.sh`, which falls back to `WANDB_MODE=offline`. Without it a run
  hangs in `atexit` teardown waiting on the wandb service — the process looks *alive* at
  0% CPU with no GPU and no output (stdout block-buffered to the log and never flushed).
  Also `export PYTHONUNBUFFERED=1` so a stall is visible.
- **CLI flags are silently dropped** unless the key already exists in the target config
  yaml (`update_configs` in `main_pytorch.py`). This has bitten `--eval_query_ids`,
  `--optimizer`, and `--early_stop_patience`. `snorkel_finance_gym.yaml` declares
  `train_task_ids`/`eval_task_ids` as `null` **specifically** so those flags can be passed.
  If a flag seems ignored, grep the yaml before debugging anything else.
- **GPU memory.** One 4B rollout run peaks around 55–70 GiB on an H100; assume one run per
  GPU. Sample `nvidia-smi` repeatedly — between batches it reads a few MiB and looks idle
  when it is not.
- **Don't `kill -9` a driver alone.** Its `run_*_sweep.sh` child is reparented to init and
  keeps going, racing whatever you start next. Kill the process group:
  `kill -TERM -$(ps -o pgid= -p <pid> | tr -d ' ')`.

## 9. Minimal smoke sequence on a fresh box

```bash
scripts/setup_new_box.sh
git clone --branch v1.0.0 https://github.com/sierra-research/tau2-bench.git   # GitHub-capable shell
export https_proxy=http://fwdproxy:8080 http_proxy=http://fwdproxy:8080
UV_PROJECT_ENVIRONMENT=.venv-tau2 uv sync --extra tau2
scripts/prefetch_models.sh
ls tau2-bench/data && ls data/snorkel_finance/benchmark      # data present?
SMOKE=1 ./scripts/run_sft_rollout_eval.sh                    # user-sim path alive?
uv run --no-project python scripts/check_rollout_valid.py <the run dir>
```

If the smoke run passes validity, the full sweep is safe to launch.
